## 1. Mục tiêu, căn cứ và phạm vi

DOC 5.2 của manual yêu cầu xác định giao diện giữa component, wireframe và hệ ngoài; mẫu đầu ra của manual dùng OpenAPI/REST. Vì vậy tài liệu này dùng schema và operation GraphQL làm hợp đồng FE-BE thay cho REST endpoints; không tạo các REST CRUD trùng chức năng. Đây là bản thiết kế hợp đồng, không phải schema Strawberry đã triển khai. Tên operation, trường và DTO dưới đây là đề xuất dùng để review; phải được đồng bộ vào schema thực tế và kiểm thử tích hợp trước khi xem là đã chốt.

### 1.1 Đồng bộ kỹ thuật bắt buộc

- **SQLAlchemy 2.0 Sync + Psycopg 3** sau Repository Layer (ADR-DATA-002). Resolver GraphQL chạy trong threadpool; không dùng async session. Adapter ngoài dùng `httpx` sync cho v1.
- **Transaction theo use case** (ADR-DATA-003): một mutation ghi chỉ commit khi toàn bộ thay đổi chính hợp lệ. Gửi push/email và xóa object ảnh được thực hiện sau commit, lỗi của chúng không rollback dữ liệu chính.
- **Keyset pagination** (ADR-DATA-004): lọc quyền/chặn trước rồi mới giới hạn trang; không offset.
- **Không trộn sync/async** trong cùng luồng request. DOC 4.2-A và ADR-BE-005 hiện vẫn mô tả async nên cần cập nhật để không mâu thuẫn ADR-DATA-002; nếu Lead/DB đổi lại async, phải sửa đồng thời DOC 4.2-A, ADR-BE-005, DOC 5.1-A và DOC 5.2-A.

## 2. Biên giao tiếp

| Bề mặt | Client / caller | Giao thức và trách nhiệm |
|---|---|---|
| Public API | Flutter FE → P1–P4 | GraphQL qua HTTPS; query đọc, mutation ghi; schema là nguồn hợp đồng. |
| Media upload | Flutter → P2 (HTTP multipart) → B4 → X1 | HTTP `multipart/form-data` tới backend, **không gọi trực tiếp nhà cung cấp ảnh**. Đây là bước con trong tạo/sửa bài hoặc cập nhật hồ sơ, không phải UC riêng. |
| Internal component APIs | P1–P4 → B1–B10 → D1–D4/X1–X4 | Lời gọi nội bộ theo interface của DOC 5.1; không phải public HTTP và không gọi vòng qua GraphQL. |
| External integrations | X1–X4 → E3–E6 và dịch vụ email | Lời gọi server-side qua adapter. E6 là GPS thiết bị + logic bbox/Haversine phía server, không phải adapter ngoài. |

**E6 không phải adapter.** Vị trí do client gửi trong `LocationInput`; B8 xử lý bbox/Haversine với bảng `restaurants` qua D4/D2. Không có “Location Adapter” để gọi.

## 3. API overview

### 3.1 Base URL và transport

| Môi trường | URL |
|---|---|
| Local theo System Context | `http://localhost:8001/graphql` |
| Môi trường công khai | `https://<backend-host>/graphql` qua nginx/reverse proxy; hostname triển khai chưa chốt. |
| Media upload | `POST https://<backend-host>/media/uploads`; local tương ứng `http://localhost:8001/media/uploads`. |

GraphQL nhận `POST` với JSON `{ "query": "...", "variables": { ... }, "operationName": "..." }`, `Content-Type: application/json`. Không dùng GET cho mutation. Mọi operation đi qua `/graphql`; danh mục operation bên dưới thay cho một URL REST cho từng use case.

Header chung:

| Header | Bắt buộc | Ghi chú |
|---|---|---|
| `Authorization: Bearer <accessToken>` | Với operation cần phiên và upload media | Dùng cùng access token; không có token riêng cho upload. |
| `Content-Type: application/json` | GraphQL | Upload dùng `multipart/form-data`. |
| `X-Request-Id` | Không | Nếu client gửi, server echo lại; nếu không, server sinh mới. |
| `X-Client-Platform: web \| android \| ios` | Nên gửi | Quyết định refresh token trả trong body (native) hay set cookie HttpOnly (web). |

### 3.2 Quy ước dữ liệu

- Tên field GraphQL dùng `camelCase`; enum dùng `SCREAMING_SNAKE_CASE`. ID là opaque `ID`, không đưa khóa database ra contract.
- Mọi danh sách dài dùng cursor opaque, không dùng offset. Mặc định 10 phần tử; `first` tối đa 50 (NFR-02); `PageInfo` trả `endCursor` và `hasNextPage`.
- Lỗi nghiệp vụ dùng `errors[].extensions.code` ổn định; message là tiếng Việt thân thiện, không phải chuỗi để FE so sánh.
- Không trả mật khẩu, password hash, OTP, reset token thô trong log, JWT trong log hoặc thông tin cấu hình nhà cung cấp. **Email không xuất hiện trong bất kỳ profile type nào.**
- Thời gian dùng ISO-8601 UTC; tọa độ theo độ thập phân WGS84. Không dùng `Float` cho giá; dùng enum `PriceRange` theo schema.
- `null` khác với “không có quyền xem”: field bị ẩn bởi `publicFields` trả `null` và được liệt kê thiếu trong `visibleFields`; không trả dữ liệu riêng rồi để FE ẩn.

## 4. Authentication & security

### 4.1 Mô hình token

Thiết kế theo DOC 5.4-A: **phiên 7 ngày** được biểu diễn bằng refresh token 7 ngày; access token ngắn 30 phút để gọi API. Điều này đáp ứng NFR-06 (“phiên đăng nhập dùng token JWT hết hạn sau 7 ngày”) và API-FE-05, đồng thời tránh một token dài hạn bị lộ.

| Trường | Hợp đồng |
|---|---|
| Access token | JWT 30 phút, gửi qua `Authorization: Bearer`. Claims tối thiểu: `sub`, `jti`, `typ=access`, `ver`, `exp`, `iat`. |
| Refresh token | JWT 7 ngày, claims tương tự với `typ=refresh`, `jti` riêng. Native nhận trong body; web nhận bằng cookie `HttpOnly; Secure; SameSite=Strict` và không đọc được bằng JS. |
| Refresh | `refreshSession(refreshToken: String)` cấp access mới + refresh mới (rotation). Refresh cũ bị đưa vào `revoked_tokens`; dùng lại refresh đã thu hồi bị từ chối. |
| Logout | `logout(refreshToken: String)` cần access token còn hiệu lực trong header + refresh token trong body/cookie; thu hồi **cả hai `jti`**. Nếu access đã hết hạn, FE gọi refresh rồi logout. |
| Kiểm tra access | Ngoài chữ ký/hạn, backend tra `revoked_tokens` theo `jti` của access. Không chỉ dựa vào việc FE xóa token. |
| Reset mật khẩu | Thành công thì tăng `users.token_version`; mọi access/refresh cũ có `ver` thấp hơn bị từ chối. Đáp ứng “vô hiệu hóa toàn bộ phiên cũ”. |
| Logout idempotent | Token đã thu hồi/hết hạn nhưng chữ ký hợp lệ vẫn trả `success: true`; không tạo lỗi cho FE. |
| HTTPS | Bắt buộc khi triển khai công khai; local được phép HTTP. |
| CORS | Chỉ cho phép origin FE đã cấu hình qua biến môi trường; `allow_credentials=true` khi dùng cookie; không wildcard. Expose `X-Request-Id`. |
| CSRF | Với web dùng cookie refresh: `SameSite=Strict` + kiểm tra `Origin`; không dùng cookie cho mutation nếu thiếu kiểm tra origin. Mobile dùng header nên không có CSRF cookie. |
| Correlation | `X-Request-Id` được echo trong response và `errors[].extensions.requestId`; không đưa bí mật vào log. |

**Vì sao cần `revoked_tokens` cho access:** REQ-006 yêu cầu token cũ không dùng được sau logout. Nếu chỉ xóa token ở FE hoặc chỉ thu hồi refresh, access còn hạn tới 30 phút vẫn dùng được. Vì vậy access `jti` cũng được ghi vào bảng thu hồi và kiểm tra mỗi request cần phiên. Chi phí là một truy vấn unique index `jti`; chấp nhận được ở quy mô v1.

### 4.2 Quyền theo operation

- **Không cần phiên:** `register`, `login`, `refreshSession`, `requestPasswordReset`, `verifyPasswordResetOtp`, `resetPassword`; các query đọc công khai: `feed`, `post`, `profile`, `profilePosts`, `search`, `trending`, `nearbyPlaces`, `randomDish`.
- **Cần access token hợp lệ:** `logout`, `registerDevice`, `unregisterDevice`; các query cần phiên: `myProfile`, `myPosts`, `myCollections`, `collectionItems`, `notifications`, `assistantSessions`, `assistantHistory`; toàn bộ mutation bài/hồ sơ/tương tác/báo cáo/collection/notification/assistant; upload media.
- **Refresh token thay access:** `refreshSession` chỉ cần refresh token hợp lệ (access có thể đã hết hạn).
- **Quyền sở hữu:** chủ bài mới được sửa/xóa bài; chủ hồ sơ mới được sửa hồ sơ/quyền riêng tư; chủ collection mới quản lý collection riêng; chủ thông báo mới đánh dấu đọc; chủ phiên chat mới đọc/retry. Kiểm tra ở lớp Business qua B10, không tin trạng thái FE.
- **Khách / phiên hết hạn:** mutation bị từ chối bằng `UNAUTHENTICATED`; FE chuyển login và quay lại ngữ cảnh. Sau login, FE yêu cầu người dùng bấm lại; backend không tự thực hiện mutation đang chờ.
- **Riêng tư:** `PublicProfile` chỉ trả trường được chủ cho công khai; email luôn bị từ chối. Hồ sơ/bài của người bị chặn bị lọc theo REQ-028.
- Không có vai trò Admin trong API v1. Báo cáo không tự ẩn bài.

### 4.3 OTP, reset và brute-force

Các con số dưới đây đã thống nhất giữa NFR-06, REQ-003/004/005 và DOC 5.4-A, nên là baseline của hợp đồng (không còn là “đề xuất”):

| Quy tắc | Giá trị |
|---|---|
| OTP | Đúng 6 chữ số; hiệu lực 10 phút; tối đa 5 lần sai; sai lần thứ 5 làm mã vô hiệu. |
| Reset grant | Chuỗi ngẫu nhiên dùng một lần; hiệu lực 15 phút; backend chỉ lưu hash. |
| Gửi lại OTP | Chính sách throttle chưa có con số trong NFR; response trả `retryAfter` nếu đã cấu hình. Không tự đặt số giây. |
| Chống dò tài khoản | `requestPasswordReset` luôn trả thông báo chung; không tiết lộ email có tồn tại. |
| Lỗi gửi email | `EMAIL_DELIVERY_FAILED` là mã **nội bộ** (log/metric); response public vẫn là thông báo chung, không trả mã này để tránh dò account. |
| Đăng nhập | Sai email/mật khẩu trả cùng một mã `INVALID_CREDENTIALS`; không nói field nào sai. |

Rate limit cho login/OTP/API chưa có ngưỡng được duyệt; xem §12.

### 4.4 Thiết bị nhận push

`registerDevice(fcmToken, deviceType)` và `unregisterDevice(fcmToken)` cần phiên. Backend upsert theo `(user_id, fcm_token)`; gọi lặp không tạo bản ghi trùng. Token FCM không bao giờ trả lại cho client khác. Đăng xuất không tự xóa thiết bị (người dùng có thể đăng nhập lại); unregister được gọi khi người dùng tắt thông báo hoặc logout tùy chọn UI.

**Ghi chú nullability và quyền riêng tư:**

- `Post.isLikedByViewer`/`isSavedByViewer` là `null` với khách; `false` với người đã đăng nhập chưa tương tác.
- `PublicProfile` luôn công khai `id`, `username`, `displayName`. Các field còn lại chỉ trả khi nằm trong `publicFields`; `visibleFields` cho FE biết chính xác trường nào đang công khai. `avatarUrl` bị ẩn nếu `AVATAR` không công khai; `postCount` ẩn nếu `POSTS` không công khai; `followerCount`/`followingCount` ẩn theo field tương ứng.
- `UserSummary` (author trong `Post`, actor trong `Notification`) chỉ là danh tính tối thiểu: luôn có `id`/`username`/`displayName`; `avatarUrl` trả `null` nếu chủ hồ sơ không công khai `AVATAR`.
- `Post` lồng trong kết quả khác — `SearchResult.post`, `NearbyPlace.relatedPost`, `DishSuggestion.relatedPost`, `Notification.post` — áp dụng cùng quyền xem như `post(id)`; bài ẩn/đã xóa/người bị chặn trả `null` (hoặc `targetAvailable=false` với notification), không trả nội dung rồi để FE ẩn.
- `OwnProfile` không trả email. Nếu sau này cần email cho màn quản lý tài khoản, phải thêm operation riêng có kiểm tra phiên; không mở rộng `PublicProfile`.
- `username` do server sinh từ `displayName`/email local-part, duy nhất, không đổi trong v1. Đây là handle ổn định; FE không cho sửa vì MH-02/MH-11 không có trường username. Nếu Lead muốn người dùng tự chọn username, phải bổ sung input và wireframe trước khi chốt.
- `Notification.message` được sinh từ `type` + dữ liệu hiện tại; FE không so sánh chuỗi. `actor`/`post` có thể null; `targetAvailable=false` khi đích đã xóa/ẩn/không còn quyền xem; MH-14 hiển thị “Đích không khả dụng” và chỉ cho quay lại.
- **Mặc định công khai đề xuất:** `displayName` luôn công khai; `publicFields` gồm `AVATAR`, `BIO`, `POSTS`, `FOLLOWER_COUNT`, `FOLLOWING_COUNT`; `CITY` và `SOCIAL_LINKS` riêng tư. Đây là lựa chọn sản phẩm cần Lead/FE chốt (§12.2).
- `users.is_private` trong 5.3-A **không thay thế** `publicFields`: v1 dùng allowlist từng trường để đáp ứng REQ-015; `is_private` dành cho chế độ tài khoản riêng tư khi có UC riêng.
- `NotificationType.NEW_POST_FROM_FOLLOWING` giữ theo schema nhưng v1 **chưa phát sinh** vì follow không đổi feed và chưa có fan-out khi đăng bài. Bật thì phải thêm bước tạo notification sau commit `createPost` và đo tải.

- `refreshSession` và `logout` nhận `refreshToken` tùy chọn vì web dùng cookie; native gửi body. Thiếu cả hai nguồn → `UNAUTHENTICATED`.

- `useAssistantDraft` là mutation idempotent nhưng **không tạo bài**; nó chỉ trả draft đã lưu để FE prefill MH-08.
- Ngữ cảnh gửi X4/E5 chỉ gồm dữ liệu công khai đã lọc `is_hidden` và block; không gửi email, token, mật khẩu, media riêng tư hoặc trường hồ sơ không công khai. Tham chiếu AI trả về phải đối chiếu lại với dữ liệu người gọi được xem.

### 5.4 Quy tắc dữ liệu bài và quán

- **Món:** `dishName` được trim, kiểm tra không rỗng, chuẩn hóa chữ thường/bỏ dấu/thu gọn khoảng trắng; backend tái sử dụng `dishes` theo `name_normalized` hoặc tạo mới (REQ-027).
- **Thẻ:** mỗi thẻ trim, bỏ dấu `#`, chuẩn hóa; tái sử dụng `tags` theo `name_normalized`; tối đa 10 thẻ/bài (đề xuất, xem §11).
- **Giá:** chỉ nhận enum `PriceRange`, không nhận số thực. FE hiển thị nhãn tương ứng; backend không tự suy ra khoảng giá từ số tiền.
- **Công thức:** nếu có bất kỳ field nào trong `recipe`, backend trả object `Recipe`; `ingredients`/`steps` mặc định `[]` nếu không có. Không lưu công thức dạng một chuỗi.
- **Ảnh:** thứ tự trong `images` là thứ tự hiển thị; `position` bắt đầu từ 0. Ảnh đầu tiên là ảnh đại diện bài trong feed nếu có.
- **Quán:** nếu `restaurantId` có, backend kiểm tra tồn tại và dùng làm liên kết. Nếu không, đề xuất B4 tìm quán theo tên chuẩn hóa + khoảng cách ≤100 m; nếu không thấy thì tạo `restaurants` mới với tên/địa chỉ/tọa độ. Nếu Lead/DB không duyệt tự tạo quán, bài chỉ có location tự do sẽ không xuất hiện trên bản đồ; khi đó phải ghi rõ giới hạn này trong MH-17.
- **Ẩn/xóa:** `is_hidden` do moderation tương lai đặt; API v1 không có mutation ẩn bài. Mọi query đọc loại bài `is_hidden=true`; báo cáo không đặt cờ này (REQ-020).
- **Xóa:** xóa vật lý bài; FK cascade dọn `post_images`, `post_tags`, `likes`, `collection_items`, `reports`. Sau commit, backend xóa object ảnh qua X1; nếu lỗi, job dọn dẹp thử lại. Thông báo cũ trỏ tới bài đã xóa trả `targetAvailable=false`.
- **Caveat tombstone:** xóa vật lý làm mất bản ghi để xác minh chủ ở lần gọi lặp. Hợp đồng trả `alreadyDeleted=true` cho lần lặp thay vì `NOT_FOUND`; muốn chặt quyền hoặc audit phải thêm tombstone/`post_deletions` — xem quyết định mở §12.2.

## 7. Media upload — hợp đồng HTTP bổ sung

FE tách `IMedia.upload` khỏi GraphQL transport nhưng chưa chốt giao thức/route. Hợp đồng dưới đây là đề xuất cần FE/BE/DB duyệt; là bước con của REQ-010, không phải UC riêng.

### 7.1 Request/response

| Thuộc tính | Hợp đồng |
|---|---|
| Request | `POST /media/uploads`; `Authorization: Bearer <accessToken>`; `Content-Type: multipart/form-data`; field `file` (một file) và `purpose` (`POST_IMAGE` mặc định, `AVATAR`, `COVER`). |
| Validation | Ảnh hợp lệ (đề xuất JPEG/PNG/WebP), tối đa 10 MB trước xử lý; xác minh magic bytes, không tin MIME client khai; resize cạnh dài ≤1600 px; strip EXIF; từ chối file không phải ảnh. |
| Success | `201` JSON `{ "mediaId": "...", "url": "https://...", "width": 1200, "height": 800, "purpose": "POST_IMAGE", "expiresAt": "..." }`. Client chỉ dùng `mediaId`; không gửi URL tự do vào `createPost`/`updateProfile`. |
| Pending | Media mới ở trạng thái `pending`, thuộc người upload, hết hạn sau 24 giờ nếu chưa được dùng. |
| Validation error | `413` quá dung lượng; `415` không phải ảnh hỗ trợ; body `{ "error": { "code", "message", "requestId" } }` với `MEDIA_INVALID`. |
| Provider error | `502`/`503` với `MEDIA_UNAVAILABLE`; FE giữ file và cho chọn thử lại / bỏ ảnh và đăng text / hủy. Không có bài nào được tạo bởi lần upload thất bại. |
| Auth error | `401` thiếu/hết hạn token; `403` không có quyền với media của người khác. |

Route/status/payload là **đề xuất cần xác nhận**; không bắt buộc dùng REST cho resource khác. Cấu hình provider/secret chỉ ở backend qua biến môi trường; không gọi trực tiếp Cloudinary/nhà cung cấp ảnh từ FE.

### 7.2 Vòng đời media và tính nguyên tử

1. Upload thành công → tạo `media_uploads(status=pending, owner_id, purpose, storage_key, url, …)`.
2. `createPost`/`updatePost`/`updateProfile` nhận `mediaId`; backend kiểm tra **cùng chủ**, **đúng purpose**, **chưa consumed**, **chưa hết hạn**.
3. Trong cùng transaction với thao tác chính: gắn media vào `post_images`/`users.avatar_url`/`users.cover_url` và đặt `status=consumed`. Nếu bất kỳ media nào sai, toàn bộ mutation rollback; media vẫn `pending` để FE thử lại.
4. Khi sửa bài bỏ ảnh hoặc xóa bài: đánh dấu media `deleted`, sau commit gọi X1 xóa object; nếu X1 lỗi, job dọn dẹp thử lại. Không rollback bài chỉ vì xóa object thất bại.
5. Job dọn dẹp định kỳ xóa object và đánh dấu `deleted` cho media `pending` quá 24 giờ hoặc `consumed` nhưng bài đã bị xóa.
6. Media đã consumed không được dùng lại ở bài khác; cố dùng lại → `MEDIA_ALREADY_CONSUMED`.

**Thành công một phần:** không có. Nếu một trong nhiều ảnh không hợp lệ/không thuộc người dùng, không tạo bài và không tiêu thụ ảnh nào. FE chỉ được tự bỏ ảnh khi người dùng chọn “Bỏ ảnh và đăng bài” (REQ-010 AC-4); backend không tự chuyển sang bài text.

## 10. Common errors và HTTP behavior

### 10.1 GraphQL errors

Response có thể chứa `data`, `errors`, hoặc cả hai. Mỗi error chuẩn hóa dùng:

```json
{
  "message": "Thông báo tiếng Việt dành cho người dùng.",
  "path": ["operationName"],
  "extensions": {
    "code": "ERROR_CODE",
    "fieldErrors": [{ "field": "fieldName", "code": "FIELD_CODE" }],
    "requestId": "req_..."
  }
}
```

`fieldErrors` và `path` có thể vắng mặt nếu không áp dụng. Không trả stack trace, SQL, đường dẫn nội bộ, raw provider response hoặc bí mật. Lỗi mutation không được tạo success-shaped fallback. Lỗi hệ thống được log phía server và trả thông báo tổng quát.

| Code | Dùng khi | FE nên làm |
|---|---|---|
| `VALIDATION_FAILED` | Input sai; tên món/lý do rỗng, query ngắn, field sai, media sai purpose | Hiển thị lỗi theo field; không tự gửi lại. |
| `UNAUTHENTICATED` | Thiếu/hết hạn/không hợp lệ access/refresh; `ver` cũ sau reset | Xóa phiên cục bộ, chuyển login; không retry mù. |
| `FORBIDDEN` | Không phải chủ tài nguyên hoặc không có quyền | Báo không đủ quyền, không thử lặp. |
| `NOT_FOUND` / `NOT_AVAILABLE` | Tài nguyên không tồn tại, đã xóa/ẩn hoặc không được phép xem | Trạng thái không khả dụng, không lộ nội dung riêng. |
| `CONFLICT` | Bài thay đổi đồng thời (`expectedUpdatedAt` lệch) hoặc unique constraint | Làm mới dữ liệu; conflict policy chính thức chờ DOC 6.2. |
| `ALREADY_EXISTS` | Email hoặc tên collection trùng | Báo lỗi theo field; không tạo trùng. |
| `INVALID_CREDENTIALS` | Sai email/mật khẩu | Thông báo chung; không nói field nào sai. |
| `ACCOUNT_CREATED_LOGIN_REQUIRED` | Đăng ký đã tạo account nhưng không lập được phiên | Hướng dẫn đăng nhập; không gửi lại đăng ký. |
| `RATE_LIMITED` | Vượt ngưỡng đã cấu hình/duyệt | Chờ theo `retryAfter` nếu có; không tự đoán. |
| `MEDIA_INVALID` | Tệp sai định dạng/quá lớn | Giữ form; yêu cầu chọn/đổi tệp. |
| `MEDIA_UNAVAILABLE` | Provider ảnh tạm lỗi | Giữ tệp; đưa 3 lựa chọn theo REQ-010. |
| `MEDIA_NOT_FOUND` / `MEDIA_ALREADY_CONSUMED` | Media không tồn tại/không thuộc người dùng/đã dùng | Yêu cầu upload lại; không dùng lại ID cũ. |
| `DEFAULT_COLLECTION_PROTECTED` | Xóa/đổi tên collection mặc định | Không hiển thị thao tác hoặc báo không được phép. |
| `EMAIL_DELIVERY_FAILED` (nội bộ) | Không thể gửi OTP | **Không trả ở response public** của `requestPasswordReset`; chỉ log/metric để tránh dò account. Muốn báo trực tiếp phải chấp nhận rò rỉ account hoặc thêm kênh xác nhận ngoài. |
| `SERVICE_UNAVAILABLE` | Dịch vụ phụ thuộc tạm không khả dụng | Hiển thị lỗi có thể thử lại; luồng không phụ thuộc vẫn hoạt động. |
| `OUTCOME_UNKNOWN` | Mất phản hồi, chưa xác nhận trạng thái ghi | Không tự submit lại; kiểm tra trạng thái hiện có. |
| `INTERNAL` | Lỗi không dự kiến | Thông báo chung + request ID; không hiển thị chi tiết server. |

**Lỗi trợ lý AI** dùng `AssistantFailure.code`, không dùng `errors[].extensions.code`: `AI_TIMEOUT`, `AI_UNAVAILABLE`, `INVALID_OUTPUT`, `NO_DATA`. `retryable=true` với timeout/unavailable/invalid output; `NO_DATA` vẫn cho hỏi tiếp nhưng không hứa có kết quả.

### 10.2 HTTP upload / transport status

| Status | Áp dụng | Body |
|---|---|---|
| `200` | GraphQL response đã xử lý | GraphQL `{data, errors}`. |
| `201` | Upload thành công | JSON media. |
| `400` | JSON/GraphQL document không hợp lệ hoặc multipart lỗi cú pháp | Lỗi transport tổng quát, không stack trace. |
| `401` | Upload/refresh thiếu hoặc sai credential | Error JSON chuẩn; GraphQL auth thường trả `UNAUTHENTICATED` trong `errors`. |
| `403` | Không có quyền với media/tài nguyên | Error JSON chuẩn. |
| `413` | Upload vượt 10 MB | `MEDIA_INVALID`. |
| `415` | Nội dung không phải ảnh hỗ trợ | `MEDIA_INVALID`. |
| `502`/`503` | Provider ảnh không đáp ứng | `MEDIA_UNAVAILABLE`. |
| `500` | Lỗi server không dự kiến | Error chung + request ID. |

Status upload phải khớp gateway/nginx khi triển khai. GraphQL transport thường trả HTTP 200 cho operation đã xử lý, kể cả khi có `errors`.

## 11. Pagination, validation, versioning và compatibility

### 11.1 Pagination/filtering

- Cursor opaque, gắn với thứ tự sắp xếp ổn định; server không nhận offset hoặc cursor tự chế.
- `first` mặc định 10, cap 50; nhỏ hơn 1 → `VALIDATION_FAILED`; lớn hơn 50 được giới hạn về 50 (NFR-02).
- Cursor áp dụng cho feed, search, profile posts, my posts, collections/items, notifications, assistant sessions/history.
- **Lọc trước, giới hạn sau:** `is_hidden`, block hai chiều, quyền xem hồ sơ phải áp dụng trước khi lấy `first` để trang không bị thiếu bất ngờ (ADR-DATA-004).
- Feed `LATEST`/`TRENDING`; follow không đổi feed. `TRENDING` dùng `likes_count DESC, created_at DESC, id DESC`; cửa sổ thời gian “đang hot” chờ DOC 7.1, hiện không tự thêm điều kiện ngày nếu chưa duyệt.
- Search tối thiểu 2 ký tự, không dấu; kết quả loại bài ẩn và người bị chặn. Filter `kinds` thu hẹp món/quán/bài; “Khu vực” của MH-15 chưa có cột chuẩn hóa nên chưa nhận tham số area (xem §12).
- Nearby mặc định 5 km, tối đa 50 kết quả, gần trước; không tự mở rộng bán kính, FE gợi ý đổi khu vực/bán kính theo AC-3.
- Trending đọc snapshot 7 ngày; nếu chưa có snapshot trả `state=WAITING`, danh sách rỗng, không lỗi. Điểm/trọng số chờ DOC 7.1.
- Assistant history trả mới nhất trước; FE đảo khi render; `hasNextPage` nghĩa là còn tin nhắn cũ hơn.

### 11.2 Giới hạn validation

### 11.3 Versioning / schema evolution

GraphQL schema là một contract dưới `/graphql`; **không áp `/v1` cho từng operation** vì ADR-BE-002 chọn GraphQL, không phải REST versioning. Versioning theo evolution của schema:

1. Bổ sung field/type/operation không bắt buộc là backward-compatible.
2. Không đổi ý nghĩa hoặc kiểu field hiện có theo cách phá vỡ client.
3. Field sắp bỏ phải đánh dấu deprecated, có lý do và thay thế; thông báo FE trước khi xóa.
4. Thay đổi breaking chỉ sau khi FE/BE/Lead chấp thuận; khi cần nhiều client song song, chọn endpoint/schema version riêng bằng quyết định mới.
5. Schema snapshot/introspection hoặc generated client là artifact review; integration test kiểm operation FE đang dùng.
6. Media upload version cùng ứng dụng; route/deprecation phải chốt đồng bộ với GraphQL.

## 14. Acceptance checks trước khi chốt contract

### 14.1 Điều kiện API-FE-01…12

- [ ] **API-FE-01:** schema có tên operation, kiểu, nullability và ví dụ cho các luồng chính (feed, tạo bài, lỗi, trợ lý).
- [ ] **API-FE-02:** phân biệt công khai/ghi/chủ sở hữu; thiếu token và sai chủ bị từ chối; public profile không email.
- [ ] **API-FE-03:** HTTP, GraphQL error và lỗi nghiệp vụ có mã ổn định; field error trỏ đúng input; không lộ stack/token.
- [ ] **API-FE-04:** cursor mặc định ≤10, tối đa 50; `hasNextPage` rõ; tải thêm không phụ thuộc offset.
- [ ] **API-FE-05:** phiên 7 ngày qua refresh token; OTP/reset đúng NFR-06; logout vô hiệu phiên server; revoke/gửi lại OTP có chính sách.
- [ ] **API-FE-06:** HTTPS khi public; CORS cho web; header auth/content-type; CSRF khi dùng cookie.
- [ ] **API-FE-07:** toggle/gửi lặp/mất phản hồi có ngữ nghĩa; desired-state, delete/report idempotent; create/register nêu rõ giới hạn retry.
- [ ] **API-FE-08:** upload có giao thức, giới hạn, vòng đời tệp mồ côi, quyền dùng ảnh, không thành công một phần.
- [ ] **API-FE-09:** xóa bài dọn dữ liệu phụ thuộc; collection mặc định không xóa; bỏ lưu xác định phạm vi.
- [ ] **API-FE-10:** version/evolution, base URL theo môi trường và cách nhận `X-Request-Id`.
- [ ] **API-FE-11:** 429/rate limit/retry-after nếu có; hạn gửi lại OTP không do FE tự đặt.
- [ ] **API-FE-12:** hiệu năng NFR-01/03/04 có môi trường đo; timeout AI và fallback rõ.

### 14.2 Kiểm tra nội bộ tài liệu

- [ ] Mọi REQ-001…REQ-028 có operation/transport tương ứng trong ma trận; MH-01…MH-19 có query/mutation hoặc được nêu rõ là client-only.
- [ ] Mọi mutation (ngoại trừ register/login/refresh/recovery/logout) yêu cầu phiên; B10/Business kiểm quyền và chủ sở hữu.
- [ ] Không có adapter địa lý ngoài; không còn `imageUrl` đơn, `price: Float`, `recipe: String`, `MediaAction`, `uploadedMediaId` trong hợp đồng.
- [ ] `Post`/`PostInput`/`PostUpdateInput`/`AssistantDraft` khớp schema 5.3-A hoặc có gap DB tương ứng ở §1.2.
- [ ] `Notification` có actor/post/targetAvailable; `markAllNotificationsRead` có trong 5.1 và 5.2.
- [ ] `logout` thu hồi cả access và refresh; reset mật khẩu hủy phiên cũ; không chỉ xóa token ở FE.
- [ ] Block filter áp dụng trước pagination; v1 không có mutation chặn vì FR chưa có UC.
- [ ] Delete/report semantics không tự ẩn bài, không xóa lặp, không tạo bài text khi media lỗi.
- [ ] Các quyết định mở ở §12 được Lead/FE/DB xác nhận trước triển khai production.
- [ ] Schema GraphQL thực tế được so với operation catalog và integration test; không tuyên bố bản nháp này là OpenAPI hay schema đã code-first thực thi.
