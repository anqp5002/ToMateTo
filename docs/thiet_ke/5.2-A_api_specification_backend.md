## 2. Tổng quan giao tiếp

### 2.1 Giao thức và URL

| Môi trường | GraphQL | Upload ảnh |
|---|---|---|
| Local | `http://localhost:8001/graphql` | `http://localhost:8001/media/uploads` (đề xuất, cần xác nhận với BE) |
| Public | `https://<backend-host>/graphql` | `https://<backend-host>/media/uploads` |

GraphQL dùng `POST` với JSON gồm `query`, `variables` và tùy chọn `operationName`. Dùng `Content-Type: application/json`. Upload dùng `multipart/form-data`. Khi triển khai public, dùng HTTPS theo NFR-08.

### 2.2 Quy ước chung

- Tên field GraphQL dùng `camelCase`; thời gian ISO-8601 UTC; tọa độ WGS84.
- Danh sách dài dùng cursor: mặc định tối đa 10 mục, không vượt 50 mục/trang (NFR-02). Không dùng offset.
- Lỗi GraphQL có `message` và `extensions.code`; lỗi nhập liệu có thể kèm `fieldErrors` để FE gắn lỗi vào trường tương ứng.
- `Authorization: Bearer <JWT>` dùng cho thao tác cần đăng nhập. Đọc nội dung công khai không yêu cầu token.
- Không trả email trong hồ sơ công khai. Không ghi mật khẩu, OTP, token hay bí mật tích hợp vào log.

### 2.3 HTTP headers và status

| Header | Khi dùng | Hành vi |
|---|---|---|
| `Content-Type: application/json` | GraphQL | Bắt buộc. |
| `Authorization: Bearer <JWT>` | Query/mutation riêng tư và media upload | Backend xác minh chữ ký, thời hạn và user hiện tại. |
| `X-Request-Id` | Mọi request | Client có thể gửi; Backend echo hoặc tự sinh để liên kết log. Không chứa PII. |
| `Origin` | Trình duyệt web | CORS chỉ cho origin đã cấu hình; danh sách origin production còn cần chốt. |

Quy ước đề xuất cho GraphQL: HTTP `200` nếu request JSON/GraphQL được nhận và response có `data` hoặc `errors` (kể cả lỗi phân quyền/nghiệp vụ trong GraphQL); HTTP `400` cho JSON hoặc document GraphQL không parse/validate được trước khi thực thi; HTTP `401` chỉ dùng nếu middleware từ chối toàn request trước resolver. Upload dùng HTTP status riêng tại §12.8. `429` dành cho rate limit khi chính sách được bật. Cần cấu hình FastAPI/Strawberry middleware theo quy ước này.

## 3. Xác thực và phân quyền

### 3.1 Phiên đăng nhập

Theo NFR-06, Backend băm mật khẩu bằng bcrypt và phát JWT có thời hạn 7 ngày. JWT được gửi qua `Authorization: Bearer <token>`. Đăng ký thành công thiết lập phiên theo REQ-001. Chính sách refresh, thu hồi token phía server và cookie web chưa được các input hiện có chốt; cần thống nhất FE/BE trước khi triển khai logout và xử lý phiên bị lộ.

### 3.2 Quyền

| Loại thao tác | Quyền |
|---|---|
| Feed, tìm kiếm, chi tiết bài công khai, xu hướng, quán gần | Khách hoặc người dùng đã đăng nhập |
| Đăng bài, thích, lưu, theo dõi, báo cáo, chat, cập nhật hồ sơ | Người dùng có JWT hợp lệ |
| Sửa/xóa bài | Chủ bài |
| Xem thông tin riêng của hồ sơ | Chủ hồ sơ |
| Hồ sơ công khai | Chỉ trường được chủ hồ sơ công khai; email luôn bị ẩn |

Backend kiểm tra quyền ở mỗi thao tác ghi và quyền sở hữu ở phía server (NFR-07, REQ-028). Không có API quản trị trong phạm vi v1.

### 3.3 Khôi phục mật khẩu

Theo NFR-06: OTP 6 chữ số, hiệu lực 10 phút, tối đa 5 lần nhập sai; quyền đặt lại mật khẩu hiệu lực 15 phút và chỉ dùng một lần. Yêu cầu gửi lại OTP tuân theo chính sách được duyệt; input hiện chưa chốt ngưỡng/thời gian gửi lại. Với email không đủ điều kiện, phản hồi không được tiết lộ tài khoản có tồn tại hay không (REQ-003).

## 4. Schema và operation

Các kiểu dưới đây mô tả dữ liệu FE cần gửi/nhận. Chúng không khẳng định cấu trúc bảng hoặc tên cột lưu trữ.

### 4.1 Kiểu dùng chung

```graphql
scalar DateTime
scalar Cursor

input PageInput {
  first: Int = 10
  after: Cursor
}

type PageInfo {
  endCursor: Cursor
  hasNextPage: Boolean!
}

type FieldError {
  field: String!
  code: String!
  message: String!
}

type ApiError {
  code: String!
  message: String!
  fieldErrors: [FieldError!]
}
```

Mọi connection trả `edges { cursor node }` và `pageInfo`. Backend giới hạn `first` ở mức 50; giá trị không hợp lệ trả `VALIDATION_FAILED`.

### 4.2 Root schema và output models

```graphql
  register(input: RegisterInput!): AuthPayload!
```

## 5. Upload ảnh

### 5.1 Request

`POST /media/uploads`, Bearer JWT, `multipart/form-data` với một file ảnh. Giới hạn theo NFR-05: tối đa 10 MB/tệp; ảnh được xử lý để cạnh dài không vượt 1600 px. Từ chối tệp không phải ảnh hoặc vượt giới hạn bằng lỗi rõ ràng.

Phản hồi thành công đề xuất:

```json
{
  "uploadId": "opaque-id",
  "url": "https://<backend-host>/media/<opaque-id>",
  "width": 1200,
  "height": 900
}
```

FE gửi `uploadId` trong input tạo/sửa bài hoặc hồ sơ. Thời hạn upload, dọn file chưa dùng và cơ chế chống tái sử dụng cần BE xác nhận; không suy diễn thành yêu cầu schema DB.

### 5.2 Lỗi và đăng bài

Nếu dịch vụ ảnh lỗi, giữ dữ liệu người dùng đã nhập và cho chọn thử lại, bỏ ảnh để đăng bài chữ hoặc hủy. Backend không tự chuyển sang bài chữ khi user chưa chọn (REQ-010, NFR-10).

## 6. Định dạng lỗi

GraphQL validation/auth/business errors trả trong `errors[]`; FE xử lý bằng `extensions.code`, không dựa trên chuỗi message. Mã đề xuất:

| Code | Ý nghĩa |
|---|---|
| `VALIDATION_FAILED` | Input sai; có thể kèm `fieldErrors`. |
| `UNAUTHENTICATED` | Thiếu token hoặc token không hợp lệ/hết hạn. |
| `FORBIDDEN` | Đã xác thực nhưng không có quyền hoặc không phải chủ sở hữu. |
| `NOT_FOUND` | Tài nguyên không tồn tại. |
| `NOT_AVAILABLE` | Tài nguyên không được phép xem; không tiết lộ dữ liệu hạn chế. |
| `ALREADY_EXISTS` | Trùng định danh hoặc dữ liệu duy nhất theo quy tắc đã thống nhất. |
| `CONFLICT` | Xung đột khi cập nhật đồng thời; chiến lược phát hiện cần chốt. |
| `RATE_LIMITED` | Yêu cầu vượt giới hạn đã cấu hình; trả metadata thời gian thử lại nếu có. |
| `INTEGRATION_UNAVAILABLE` | Dịch vụ ngoài lỗi/quá hạn; dùng chế độ lùi khi phù hợp. |
| `INTERNAL_ERROR` | Lỗi không dự kiến; không trả stack trace hoặc bí mật. |

Backend tạo/echo request ID trong response header `X-Request-Id` để đối chiếu log. Mẫu lỗi:

```json
{
  "errors": [{
    "message": "Vui lòng kiểm tra lại thông tin.",
    "extensions": {
      "code": "VALIDATION_FAILED",
      "fieldErrors": [{"field": "dishName", "code": "REQUIRED", "message": "Tên món là bắt buộc."}]
    }
  }]
}
```

#### 7.2.2 Chênh lệch cần đồng bộ giữa DOC 5.1 và 5.2

- **Session:** DOC 5.1 liệt kê `refreshSession`, `revokeSession`, `refreshToken`, revoked-token store và thu hồi phiên cũ; DOC 4.2/NFR-06 hiện chốt baseline một JWT 7 ngày, chưa định nghĩa refresh token. 5.2 giữ `refreshSession` dạng conditional, không đưa refresh/revocation thành hành vi đã chốt. Lead/BE cần thống nhất 4.2, 5.1, 5.2 và security design trước khi code.
- **Device push:** DOC 5.1 P1/B1/D1 có `registerDevice`/`unregisterDevice`/`saveDevice`/`removeDevice`, nhưng REQ-001…028 không mô tả luồng đăng ký thiết bị hoặc input token/platform. 5.2 ghi API đề xuất cho FE review; chưa giả định token schema hay lifecycle đã duyệt.
- **Profile queries:** P3 trong catalog 5.1 liệt kê `profile`, `profilePosts`, `myProfile`, `myPosts`; P2 cũng cung cấp nhóm feed/post. GraphQL chỉ có một field mỗi tên, nên contract gán `profile`/`myProfile`/`profilePosts` cho P3 và giữ `feed`/`post` tại P2. Cần cập nhật dependency của P3 trong 5.1 để chỉ rõ đường tới B3/D2 cho `profilePosts`/`myPosts`, hoặc thống nhất chuyển các query này về P2.
- **Component API naming:** 5.1 dùng tên interface logic (`requestReset`, `verifyOtp`, `listFeed`, `getPost`, `setSave`, `getTrending`, `getNearbyRestaurants`, `chooseRandomDish`, `ask`, `retry`, `listSessions`, `getHistory`, `createPostDraft`); 5.2 public GraphQL dùng tên client-facing. Resolver mapping tương ứng: `requestPasswordReset`/`resendResetOtp`→`requestReset` (resend policy còn mở); `verifyPasswordResetOtp`→`verifyOtp`; `logout`→`revokeSession`; `feed/post`→`listFeed/getPost`; 5.1 liệt kê `myPosts/profilePosts` ở P3 nhưng cần chốt dependency tới B3/D2; `savePost/removeSavedPost`→`setSave` theo trạng thái đích; `trending/nearbyPlaces/randomDish`→`getTrending/getNearbyRestaurants/chooseRandomDish`; `askAssistant/retryAssistant/assistantSessions/assistantHistory/useAssistantDraft`→`ask/retry/listSessions/getHistory/createPostDraft`.
- **Public profile media:** B5 dùng B4/D2 media lifecycle với purpose AVATAR/COVER, không gọi X1. 5.2 upload input cần giữ `purpose` để Backend xác định ảnh bài hay avatar/cover; profile mutation chỉ tiêu thụ upload đã thuộc user hiện tại.
- **Sync/async:** DOC 5.1 v0.5 và ADR dữ liệu được nêu ở nhánh component chọn SQLAlchemy Sync + Psycopg 3, resolver chạy threadpool và `httpx` sync. DOC 4.2-A hiện mô tả async. Đây là lệch giữa hai đầu vào; 5.2 không áp đặt implementation, nhưng cần đồng bộ 4.2 trước khi triển khai resolver/adapter.

## 8. Phân trang, kiểm tra dữ liệu và phiên bản

- Cursor opaque, ổn định theo thứ tự sắp xếp; mặc định tối đa 10 và trần 50 mục/trang (NFR-02).
- Feed/search mục tiêu ≤2 giây cho ít nhất 95% request trong môi trường đo NFR-01.
- Quán gần tối đa 50 kết quả trong bán kính mặc định 5 km, sắp xếp gần trước, mục tiêu ≤2 giây (NFR-03).
- Ảnh tối đa 10 MB và cạnh dài không quá 1600 px (NFR-05).
- Mật khẩu tối thiểu 6 ký tự; không lưu plaintext. OTP/reset theo §3.3 (NFR-06).
- API public dùng HTTPS; bí mật cấu hình nạp qua biến môi trường (NFR-08).
- API dùng schema GraphQL code-first; thay đổi field tương thích được có thể bổ sung, breaking change cần thông báo và thống nhất FE/BE trước khi phát hành. GraphQL endpoint hiện không gắn `/v1`; backward-compatible fields được bổ sung theo schema, field ngừng dùng cần deprecation notice trong schema và thời hạn chuyển đổi FE/BE. Thay đổi phá vỡ cần review, phát hành schema/endpoint phiên bản mới hoặc có kế hoạch migration được Lead duyệt.

## 9. Giới hạn tốc độ và các điểm cần chốt

Input hiện có nêu giới hạn OTP sai 5 lần và các giới hạn kích thước/phân trang tại §8, nhưng chưa quy định quota request chung, giới hạn đăng nhập, tìm kiếm, báo cáo, gửi lại OTP hoặc quota nhà cung cấp. Không tự đặt con số. Trước khi public deployment, BE/Lead cần chốt rate limit, cách định danh theo tài khoản/IP và metadata retry; khi áp dụng trả `RATE_LIMITED`.

Các quyết định còn mở để review:

1. Cơ chế kết thúc/thu hồi JWT khi logout và reset mật khẩu; DOC 5.1 yêu cầu refresh/revoke session nhưng NFR-06/4.2 chỉ xác định JWT 7 ngày. Chốt mô hình token và đồng bộ B1/B2/D1.
2. Semantics của input cập nhật bài: phân biệt field không gửi với `null`, và cách xóa ảnh/trường tùy chọn.
3. Upload ID, thời hạn, xóa file mồ côi và bảo đảm upload chỉ thuộc chủ tài khoản.
4. Quy tắc “đang hot”, nguồn/chu kỳ dữ liệu xu hướng và trạng thái tính năng xu hướng thẻ.
5. Quy tắc tạo/ghép quán, món, thẻ; format giá/địa chỉ và các trường hồ sơ công khai; các nguồn hiện có chưa đủ để chốt data contract chi tiết.
6. Rate limit chung và chính sách gửi lại OTP.
7. CORS và CSRF theo client web thực tế; NFR yêu cầu HTTPS nhưng chưa chốt cấu hình origin/cookie.
8. Device registration ở 5.1 (P1/B1/D1) chưa có REQ cụ thể; FE xác nhận có cần public mutation `registerDevice`/`unregisterDevice` trong v1 và chốt input token/platform.
9. DOC 5.1 P3 liệt kê `myPosts`/`profilePosts`, nhưng dependency hiện chưa nối tới B3/D2; Lead/BE cập nhật component dependency trước khi chốt owner field.

```json
      "fieldErrors": [{"field": "dishName", "code": "REQUIRED", "message": "Tên món là bắt buộc."}]
    }
  }]
}
```

## 12. Đặc tả chi tiết theo operation

Mọi operation GraphQL bên dưới dùng `POST /graphql`. Request body luôn theo dạng `{ "operationName", "query", "variables" }`; header chung là `Content-Type: application/json`, và `Authorization: Bearer <JWT>` cho operation cần đăng nhập. Response thành công nằm trong `data`; lỗi nằm trong `errors` theo §6. Mẫu `data` dưới đây thể hiện payload quan trọng, các field có thể được FE chọn theo GraphQL selection set.

### 12.1 Kiểu phản hồi dùng chung

```graphql
type User { id: ID!, displayName: String!, avatarUrl: String }
type AuthPayload { accessToken: String!, expiresInSeconds: Int!, user: User! }
type Post { id: ID!, dishName: String!, caption: String, images: [PostImage!]!, likeCount: Int!, isLikedByViewer: Boolean!, createdAt: DateTime! }
type PostImage { url: String!, position: Int! }
type Collection { id: ID!, name: String!, isDefault: Boolean!, itemCount: Int! }
type Notification { id: ID!, type: String!, actor: User, postId: ID, isRead: Boolean!, createdAt: DateTime! }
type AssistantMessage { id: ID!, role: String!, content: String!, status: String!, createdAt: DateTime!, draft: AssistantDraft }
type AssistantDraft { dishName: String, caption: String, recipe: Recipe, restaurantName: String }
type SuccessPayload { success: Boolean! }
type AcceptedPayload { accepted: Boolean!, retryAfterSeconds: Int }
type ResetGrant { resetToken: String!, expiresInSeconds: Int! }
type Profile { id: ID!, displayName: String!, bio: String, avatarUrl: String, visibleFields: [String!]! }
type VisibilityPayload { success: Boolean!, visibleFields: [String!]! }
type LikeState { postId: ID!, liked: Boolean!, likeCount: Int! }
type SaveState { saved: Boolean!, collectionId: ID }
type FollowState { followed: Boolean! }
type NotificationReadPayload { success: Boolean!, unreadCount: Int! }
type ReportReceipt { accepted: Boolean! }
type AssistantReply { sessionId: ID!, message: AssistantMessage! }
type NearbyPlacesResult { usedDefaultLocation: Boolean!, places: [NearbyPlace!]! }
type NearbyPlace { id: ID!, name: String!, latitude: Float, longitude: Float, distanceMeters: Int! }
type TrendingConnection { state: String!, edges: [TrendingEdge!]!, pageInfo: PageInfo! }
type DishSuggestion { dish: Dish, reason: String, state: String! }
```

Các output models thể hiện dữ liệu contract; kiểu `Recipe`, `Dish`, search result và connection cho collection/notification/chat cần được khai báo cùng schema thực tế sau khi data design được xác nhận. Không hiểu đoạn này là schema đã triển khai.

### 12.2 Tài khoản và khôi phục

| Operation | Request variables | Thành công | Lỗi chính / HTTP transport |
|---|---|---|---|
| `register(input)` | `email`, `password` (≥6 ký tự), `displayName` | `data.register { accessToken, expiresInSeconds, user }`; tạo tài khoản và bộ “Đã lưu” mặc định. | `VALIDATION_FAILED`, `ALREADY_EXISTS`; HTTP 200 với GraphQL errors. |
| `login(input)` | `email`, `password` | `data.login { accessToken, expiresInSeconds, user }`. | `UNAUTHENTICATED` cho thông tin sai; không tiết lộ email hay mật khẩu nào sai. |
| `refreshSession(input)` | Refresh token | `AuthPayload` mới nếu refresh model được duyệt; hiện conditional. | `UNAUTHENTICATED`; chưa bật theo baseline 4.2/NFR. |
| `registerDevice(input)` | `fcmToken`, `platform` (dự thảo) | `{success:true}`; gắn device với user hiện tại theo P1/B1/D1. | `UNAUTHENTICATED`, `VALIDATION_FAILED`; cần FE xác nhận. |
| `unregisterDevice(input)` | `fcmToken` | `{success:true}`; gỡ thiết bị thuộc user hiện tại. | `UNAUTHENTICATED`, `NOT_FOUND`. |
| `requestPasswordReset(input)` | `email` | `data.requestPasswordReset { accepted: true }`; thông báo chung dù email không tồn tại. | `VALIDATION_FAILED`; lỗi gửi email trả trạng thái có thể thử lại nhưng không tiết lộ account. |
| `resendResetOtp(input)` | `email` | `data.resendResetOtp { accepted: true, retryAfterSeconds }` nếu chính sách limit trả được thời gian. | `RATE_LIMITED`, `VALIDATION_FAILED`; quy tắc gửi lại cần Lead/BE chốt. |
| `verifyPasswordResetOtp(input)` | `email`, `otp` | `data.verifyPasswordResetOtp { resetToken, expiresInSeconds: 900 }`. | `VALIDATION_FAILED` khi sai/hết hạn/đã dùng; khóa sau 5 lần sai. |
| `resetPassword(input)` | `resetToken`, `newPassword`, `confirmPassword` (mật khẩu ≥6 ký tự, xác nhận phải trùng) | `data.resetPassword { success: true }`; reset token chỉ dùng một lần. | `UNAUTHENTICATED` khi grant sai/hết hạn/đã dùng; `VALIDATION_FAILED` nếu mật khẩu yếu hoặc xác nhận không khớp. |
| `logout` | Không có variables | `data.logout { success: true }` sau khi Backend thực thi cơ chế đã thống nhất. | `UNAUTHENTICATED`; revoke phía server hiện còn là quyết định mở (§9). |

Ví dụ đăng ký:

```json
{
  "operationName": "Register",
  "query": "mutation Register($input: RegisterInput!) { register(input: $input) { accessToken expiresInSeconds user { id displayName } } }",
  "variables": {"input": {"email": "linh@example.com", "password": "secret1", "displayName": "Linh"}}
}
```

```json
{"data":{"register":{"accessToken":"<jwt>","expiresInSeconds":604800,"user":{"id":"u_123","displayName":"Linh"}}}}
```

Ví dụ OTP đúng:

```json
{"operationName":"VerifyPasswordResetOtp","query":"mutation VerifyPasswordResetOtp($input: VerifyPasswordResetOtpInput!) { verifyPasswordResetOtp(input: $input) { resetToken expiresInSeconds } }","variables":{"input":{"email":"linh@example.com","otp":"123456"}}}
```

```json
{"data":{"verifyPasswordResetOtp":{"resetToken":"<one-time-token>","expiresInSeconds":900}}}
```

### 12.3 Feed, bài đăng và ảnh

| Operation | Request variables | Thành công | Lỗi chính |
|---|---|---|---|
| `feed(mode, page)` | `mode: LATEST/TRENDING`; `page.first`, `page.after` | `PostConnection`; `pageInfo` có cursor tiếp và `hasNextPage`. | `VALIDATION_FAILED` cho page/mode sai. |
| `post(id)` | `id` | Chi tiết bài còn khả dụng; field like-state chỉ có khi viewer login. | `NOT_FOUND`/`NOT_AVAILABLE`; không trả nội dung bài bị ẩn/không có quyền. |
| `myPosts(page)` | `page` | Connection bài do JWT owner tạo. | `UNAUTHENTICATED`. |
| `createPost(input)` | Tên món bắt buộc; caption, upload IDs theo thứ tự, thông tin quán/vị trí, giá, cảm nhận, công thức, tags nếu được xác nhận | `data.createPost { post }`; media phải hợp lệ trước khi bài được tạo. | `VALIDATION_FAILED`, `UNAUTHENTICATED`, `INTEGRATION_UNAVAILABLE`; upload lỗi không tự bỏ ảnh. |
| `updatePost(id, input)` | `id`, các field cần sửa | Bài đã cập nhật; nếu dữ liệu không đổi thì trả bản hiện tại. | `FORBIDDEN` nếu không phải chủ; `NOT_FOUND`; `CONFLICT` nếu cơ chế đồng thời được chốt và phát hiện xung đột. |
| `deletePost(id)` | `id` | `data.deletePost { success: true }`; bài không còn xuất hiện trong nội dung hoạt động. | `FORBIDDEN`, `NOT_FOUND`; xóa lặp không gây thêm thay đổi. |
| `useAssistantDraft(messageId)` | ID tin nhắn trợ lý | `data.useAssistantDraft { draft }`; FE dùng draft prefill rồi gọi `createPost`. | `FORBIDDEN` nếu message không thuộc user; `NOT_FOUND` nếu không có draft. |

Ví dụ `createPost`:

```json
{
  "operationName":"CreatePost",
  "query":"mutation CreatePost($input: CreatePostInput!) { createPost(input:$input) { id dishName caption images { url position } createdAt } }",
  "variables":{"input":{"dishName":"Phở bò","caption":"Nước dùng đậm vị","images":[{"uploadId":"up_123","position":0}],"priceRange":"MEDIUM"}}
}
```

```json
{"data":{"createPost":{"id":"p_456","dishName":"Phở bò","caption":"Nước dùng đậm vị","images":[{"url":"https://<backend-host>/media/up_123","position":0}],"createdAt":"2026-10-27T09:00:00Z"}}}
```

Sửa bài dùng semantics “field không gửi = giữ nguyên, field gửi `null` = xóa” làm đề xuất tạm thời; FE/BE phải xác nhận trước khi codegen schema vì GraphQL nullable input không tự phân biệt mọi trạng thái như mong muốn. Với ảnh, danh sách gửi được hiểu là danh sách ảnh cuối cùng nếu nhóm chốt full replacement; nếu không, cần mutation riêng thêm/xóa ảnh.

### 12.8 Upload ảnh HTTP

Request upload trả HTTP `201` và JSON đã mô tả ở §5. Lỗi HTTP dự kiến: `400` định dạng/size không hợp lệ, `401` thiếu hoặc sai JWT, `413` payload quá lớn (nếu reverse proxy chặn trước), `415` MIME không hỗ trợ, `429` khi limit được cấu hình, `502/503` khi adapter lưu trữ lỗi. GraphQL status HTTP không dùng thay cho business error; GraphQL errors thường nằm trong HTTP `200`.

Ví dụ `curl` tham khảo:

```bash
curl -X POST https://<backend-host>/media/uploads \
  -H "Authorization: Bearer <jwt>" \
  -F "file=@dish.jpg"
```

Response lỗi validation GraphQL:

```json
{"errors":[{"message":"Tên món là bắt buộc.","extensions":{"code":"VALIDATION_FAILED","fieldErrors":[{"field":"dishName","code":"REQUIRED","message":"Tên món là bắt buộc."}]}}]}
```

| `markAllNotificationsRead` | `{}` | `{"markAllNotificationsRead":{"success":true,"unreadCount":0}}` |
| `reportPost` | `{"postId":"p_1","reason":"Nội dung không phù hợp"}` | `{"reportPost":{"accepted":true}}` |
| `retryAssistant` | `{"input":{"messageId":"m_1"}}` | `{"retryAssistant":{"sessionId":"s_1","message":{"id":"m_2","status":"OK","content":"..."}}}` |
| `useAssistantDraft` | `{"messageId":"m_2"}` | `{"useAssistantDraft":{"dishName":"Phở bò","caption":null}}` |

`retryAfterSeconds` trong ví dụ OTP chỉ minh họa field, không phải mức limit đã duyệt. Các thao tác session refresh và thiết bị push trong bảng còn phụ thuộc các quyết định mở tại §7.2.2. Tương tự tên trạng thái `READY/WAITING/OK`, collection default ID và `Dish` fields là contract draft để FE/BE xác nhận.

### 12.10 Retry và idempotency

- `setLike`, `setFollow`, `markNotificationRead`, `logout`, `removeSavedPost` đặt trạng thái đích nên có thể gửi lại an toàn.
- `createPost`, `register`, `askAssistant` không tự gửi lại sau timeout nếu không có khóa idempotency. REQ-009 yêu cầu kiểm tra kết quả trước khi retry tạo bài; header `Idempotency-Key` là đề xuất cần Lead/FE/BE chốt.
- `reportPost` chống gửi lặp/rate limit chưa được nguồn quy định; không cam kết idempotent cho đến khi chốt rule.
- Mutation trả về lỗi mạng có thể là trạng thái kết quả chưa rõ; client cần query lại trạng thái trước khi gửi lần nữa.
